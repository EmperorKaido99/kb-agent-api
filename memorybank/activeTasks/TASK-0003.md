# TASK-0003: Per-user API authentication (username + token)

## Define
- **Goal**: Replace the single shared-secret `ApiKey__Key` auth with per-user credentials — each user/service gets
  a distinct username + token, so calls can be attributed and one credential can be revoked without breaking
  others.
- **Constraints**:
  - No new external auth service (Auth0, Entra ID, etc.) — free/local, matches roadmap's "no paid licences."
  - Tokens must never be stored in plaintext — only a hash, so a leaked `api-users.json` doesn't leak usable
    credentials directly.
  - Must be creatable without a chicken-and-egg problem (can't require auth to create the first user).
  - Standard HTTP mechanism preferred over a custom header scheme, for compatibility with `curl -u`, Postman, etc.
- **Definition of Done**:
  - A `dotnet run -- create-user <username>` command generates a random token, stores its hash, and prints the
    plaintext token exactly once.
  - `/api/*` requires valid `Authorization: Basic base64(username:token)` credentials matching a stored user;
    `/health` stays public.
  - No users configured = auth disabled (local dev convenience, same convention as the old `ApiKey__Key` design).
  - Unit tests for the pure logic (Basic-Auth header parsing, token hashing) pass; `dotnet build`/`dotnet test`
    green.
  - A real username+token is generated and handed to the user at the end of this task.
  - memorybank docs updated; old `ApiKeyOptions`/shared-key design removed (superseded, not run in parallel).

## Discover
- Existing `ApiKeyAuthMiddleware` + `ApiKeyOptions` (TASK-0001) implement single shared-secret auth — being
  replaced, not extended in parallel, since the user explicitly wants per-user credentials instead.
- `JsonFileIngestStateStore` (TASK-0002) is the precedent for a simple JSON-file-backed store — following the
  same pattern for user credentials, but as its own type (different semantics: username→tokenHash vs.
  path→fingerprint), not a forced shared abstraction.
- HTTP Basic Auth (`Authorization: Basic base64(user:token)`) is standard, has first-class `curl -u` support, and
  naturally carries a username alongside a secret — better fit than a custom two-header scheme for "username and
  token" as the user described it.

## Demonstrate
### Test Results
- Build: ✅ (`dotnet build` — 0 warnings, 0 errors)
- Tests: ✅ (`dotnet test` — 46/46 passed)
- **Live end-to-end verification** in this sandbox:
  - Ran `dotnet run -- create-user admin` — generated a real token, confirmed `api-users.json` stores only its
    SHA-256 hash (`{"admin":"6f8701f2..."}`), never the raw token.
  - Ran the API live and confirmed all four cases: `GET /health` without credentials → 200 (public, unaffected);
    `POST /api/ask` with no credentials → 401; with wrong credentials → 401; with the correct
    username:token via `curl -u` → passed auth and failed *downstream* on "No healthy Ollama backend" (expected —
    no live Ollama here — and proves the request got past the auth middleware, not blocked by it).
  - Generated credential and test artifacts (api-users.json, knowledge-folder-state.json) deleted after — not
    committed.
- **Not verified**: real-world use over HTTPS (Basic Auth sends credentials base64-encoded, not encrypted — relies
  entirely on the reverse proxy terminating TLS in front of this API per the roadmap's deployment model; sending
  Basic Auth over plain HTTP would expose credentials on the wire).
